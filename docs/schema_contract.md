## 1. 实库核验 vs 题目大纲差异（W1 核心发现）

通过直连实库执行只读 Schema 勘察，发现多处与选题大纲简述存在差异的关键契约细节。本智能体**严格以实库冻结 Schema 为唯一真相源**：

| 维度 | 题目大纲简述 | 实库真实 Schema | 工程适配策略 |
|---|---|---|---|
| API 节点 | `API 端点` | 拆分为 `上游API` (262) 与 `下游API` (157) | 入口暴露查 `上游API`，对外调用查 `下游API` |
| 配置与测试 | `配置文件节点`、`测试用例` | 仅存在 `配置` (1132)，实库无 `测试用例` 节点 | 禁止生成不存在标签；口语“配置/配置文件”映射为 `配置` |
| 消息交换机 | `消息通信交换机` | `消息交换机` (1) | 精确绑定 `消息交换机` |
| 归属关系 | `归属` | `归属于` (4776)，且仅覆盖 `方法->类`、`配置/队列/交换机->微服务`、`上游/下游API->方法` | **`类`/`方法` 无指向 `微服务` 的 `归属于` 边**，通过 `'ts-xxx' IN n.serviceContexts` 或 `n.moduleId` 归属微服务 |
| 调用关系 | 文本示例曾混用英文 `CALLS` | 全部使用中文 `调用` (6663)，并细分 `关系语义`（`方法调用`/`方法实现`/`服务于`/`通信边界`/`跨服务HTTP调用` 等） | 严格禁用 `CALLS`，按 `关系语义` 与中间节点标签精准隔离路径 |
| 新增关系 | 6 种关系 | 实库实际为 8 种，新增 `目标服务` (156) 与 `链中下一节点` (187) | 纳入 Schema 契约，用于跨服务目标定位与调用链验证 |
| MQ 三阶段 | 发布 / 路由 / 消费 | 均使用 `[:消息流]`，通过属性 `消息流类型` 区分 `发布至` / `路由至` / `消费自`，且所有队列共享单一 `(default)` 交换机 | **必须以 `r1.\`路由键\` = r2.\`路由键\`` 关联发布与路由阶段**，防止不同业务队列误串接 |

## 3. 关键查询拓扑模式

### 3.1 同步 RPC 下游服务发现
```cypher
MATCH (m:`方法` {nodeId: $method_node_id})
MATCH p=(m)-[r:`调用`*0..6]->(m2:`方法`)
WHERE ALL(rel IN r WHERE rel.`关系语义` IN ['方法调用', '方法实现'])
  AND ALL(x IN nodes(p) WHERE x:`方法`)
MATCH (m2)-[:`调用` {`关系语义`: '通信边界'}]->(d:`下游API`)-[:`目标服务`]->(svc:`微服务`)
RETURN DISTINCT svc.`服务名称`, svc.nodeId, d.caption
```

### 3.2 跨服务反向变更影响分析（向上追踪至入口 `上游API`）
1. **服务内反向调用**：`(caller:`方法`)-[:`调用`*0..6]->(target:`方法`)`（限定 `方法调用`/`方法实现` 且防环）
2. **本服务入口 API**：`(u:`上游API`)-[:`归属于`]->(caller)`
3. **跨服务上游调用方**：`(up_m:`方法`)-[:`调用` {`关系语义`: '通信边界'}]->(d:`下游API`)-[:`调用` {`关系语义`: '跨服务HTTP调用'}]->(u)`，再继续沿 `up_m` 的服务内反向调用找到上游服务的入口 `上游API`。

### 3.3 MQ 三阶段完整消息链路
```cypher
MATCH (pub:`方法`)-[r1:`消息流` {`消息流类型`: '发布至'}]->(ex:`消息交换机`)
      -[r2:`消息流` {`消息流类型`: '路由至'}]->(q:`消息队列`)
      -[r3:`消息流` {`消息流类型`: '消费自'}]->(sub:`方法`)
WHERE r1.`路由键` = r2.`路由键`
RETURN pub, ex, q, sub, r1.`路由键` AS routing_key
```
